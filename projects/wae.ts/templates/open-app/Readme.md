# {{nameTitle}}

`{{nameTitle}}` is an Open-X application skeleton generated by
`wae new {{name}} --template open-app`. It is the full application shape:
Rust domain crates, a platform-neutral N-API boundary, an agent CLI, published
skills, a VMZ human UI, native platform packages, and CI.

`open-tools` remains the minimal runnable tool template. Use `open-app` when the
product needs a CLI, a GUI, install/uninstall, audit, and platform packages.

## Layout

| Path | Responsibility |
|------|----------------|
| `crates/core` | Portable domain model, capability states, install planning, audit field reservation |
| `crates/napi` | Platform-neutral N-API surface over the `wae` facade |
| `packages/{{name}}` | Meta package, typed library, and the `{{name}}` CLI |
| `packages/{{name}}-ui` | VMZ page and design tokens; `wae build` stages its static delivery into the app |
| `packages/{{name}}-skills` | Agent skills with frontmatter and safety prerequisites |
| `packages/{{name}}-win32-x64` | First native platform package (`os` / `cpu` / `optionalDependencies`) |
| `wae.config.ts` | Native targets, platform packages, TS/UI/skills steps, staging and release set |

## First run

The template cannot ship lockfiles because the app name, repository, and first
dependency resolution are not known until generation.

```sh
npm install --global @wae/wae
pnpm install
git add pnpm-lock.yaml Cargo.lock
```

Commit both lockfiles before enabling CI. `check-typescript.yml` runs
`pnpm install --frozen-lockfile`, so a missing lockfile fails the job by design.
`check-rust.yml` resolves the pinned `wae` revision without `--locked` until the
first `Cargo.lock` is committed.

## Commands

```sh
pnpm run build         # wae build: native → types → TS → UI → skills → staging
pnpm run build:napi    # build one configured native target and stage it
pnpm run stage:napi    # restage an already built native artifact
pnpm run smoke:napi    # load the staged addon and verify capabilities
pnpm run check:rust    # fmt + clippy -D warnings + test
```

`wae build` reads `wae.config.ts` from the nearest parent directory, runs the
same order every time, and exits non-zero with a stable `build_*` code when a
target, artifact, platform package, skills tree, or release entry is wrong.
There is no silent skip: an unconfigured step is reported as `skipped`.

`packages/{{name}}/src/native/index.ts` is generated. The `types` step loads the staged
addon, reads its `__waeTypes` metadata, and renders one file that owns the
platform-to-package map, the TypeScript interfaces, `loadNative()`, and one
forwarder per export. Do not edit it by hand and do not import a platform package
directly: change the Rust `#[function]` / `#[object]` definitions and rebuild.
Exports are typed, so the boundary needs no hand-written interface or field
extraction in Rust.

The CLI surface is non-interactive and machine-readable where it mutates state:

```sh
{{name}} capabilities
{{name}} inspect --root <path> --limit <n> --json
{{name}} install --dry-run --json
{{name}} install --actor <id>
{{name}} uninstall --dry-run --json
{{name}} uninstall --actor <id> --keep-config
```

`install` means install-or-upgrade and is idempotent. `--dry-run` returns the
same plan shape without touching host state. Shortcut and config locations use
per-user platform standard paths. The skeleton never enables auto-start and
never elevates silently.

The generated `installApply` / `uninstallApply` intentionally return the
structured `not_implemented` capability state. Implement the platform writes in
the app domain, not in this generic N-API crate.

## Audit

Every exported N-API capability is wrapped at the boundary through
`wae::audit` (`wae.audit/v0`). The domain only supplies capability name, target
count, target summary, and a stable error code. Actor, host, session, schema,
timestamps, duration, and sanitisation stay in the shared facility. Do not add a
second audit schema.
